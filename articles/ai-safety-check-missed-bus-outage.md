東京都内のバス時刻表を集めて経路を出すサービスを個人で運用しています。
**コードはほぼ全部 Claude Code に書かせています。** 私が決めているのは
何を作るかと、公開するかどうかの判断です。

先日、定期のデータ取り込みで**特定地域の検索だけを丸ごと壊しました**。

厄介だったのは、**取り込みの安全確認もAIに設計させていて、それが
「正常」と出ていた**ことです。

## 何を作っているか

公開されているGTFSデータ（バスの時刻表の標準形式）を40事業者ぶん集めて、
2.4GBのSQLiteに固めています。都内の停留所は20,460件。そこから
「目的地へ向かう途中にバスで寄り道できる場所」を提案します。

データ源は公共交通オープンデータセンターとGTFSデータリポジトリで、
配信元が更新するので、こちらも定期的に取り込み直す必要があります。

取り込みは1時間近くかかり、その間サービスを止めます。事故が起きやすい
作業なので、AIに手順書を書かせました。退避・停止・取り込み・**突き合わせ**・
再開・切り戻し手順の表示、という流れです。

## 「突き合わせ」が正常と言った

取り込み後、その確認がこう出ました。

```
                取り込み前    取り込み後
事業者              40           40
都内停留所      20,460       20,469
路線             2,140        2,137
便            239,068      231,351
停車時刻     4,185,073    4,040,059
```

手順書には、こう書かせていました。

> ★ 事業者数・都内停留所数が**減っていないこと**を必ず確認してください。
> 減っていたらトークン切れか配信元の障害です。

事業者数は変わらず、停留所はむしろ増えています。便は3.2%減っていますが、
バスの減便は現実に起きているので、この程度なら改正の範囲です。

**確認は通りました。私もそれを見て問題ないと判断しました。**

## 実際に起きていたこと

念のため自分で八王子から検索してみたら、結果が出ません。
日付ごと・事業者ごとに数え直して、ようやく分かりました。

```
西東京バス     8/31  9/1   9/7   9/13  9/20  9/28
  取り込み前  3,358 3,358 3,358 2,741 2,741 3,358
  取り込み後      0     0     0     0     0 3,311
```

**26日間、まるごと0便。** 京王バスも当日と翌日が0でした。

原因は単純でした。配信元が**次回改正ぶんのフィードだけ**を公開していたのです。

```
西東京バス  旧: 20260829〜20260930   ← 今日を含む
            新: 20260926〜20261010   ← 26日後から15日間だけ
```

そして取り込み処理は、**今日を含まないフィードでも無条件に古いものを
差し替えます**。事業者ごとにpurgeして入れ直す作りなので、
新しいほうが期間外でもお構いなしです。

## なぜ合計では見えなかったのか

3.2%という数字が曲者でした。

- 全体から見れば誤差の範囲
- **その3.2%が八王子・青梅方面の全部だった**

合計はよく均します。40事業者のうち2社が一時的に消えても、
都営バスのような大きな事業者の便数に埋もれます。
**「全体が少し減った」と「一部が全部消えた」は、合計では区別できません。**

停留所数がむしろ増えていたのも、判断を誤らせました。停留所は
フィードの有効期間と関係なく入るので、時刻表が空でも数は減りません。

## ここがAI開発の話になる

この確認を設計したのはAIです。そして、**もっともらしく、実際に役立つ
確認でした**。トークンが切れて主要事業者が丸ごと落ちる事故は、これで防げます。

ただ、**AIが想像できた粒度でしか見ていませんでした。**

「取り込みで壊れる」と言われて思いつくのは「データが減る」です。
だから合計を比べます。しかし現実に起きたのは
「**合計はほぼ同じまま、特定の切り口だけが全滅する**」でした。

これは人間の設計者でも普通に見落とします。私も見落としました。
問題は、**AIに書かせると『確認がある』という安心だけが手早く手に入る**
ことだと思います。手順書は整っていて、注意書きまで書いてある。
中身の妥当性を疑う動機が、むしろ削がれます。

指示した側が確かめるべきだったのは、コードの正しさではなく
「**この確認は、起こりうる壊れ方を捉えているか**」でした。

## 直したこと

日付ごと・事業者ごとに数えて、**取り込み前と突き合わせる**確認を足しました。

```python
def report(conn, days, against):
    """戻り値は終了コード。空白が見つかったら 1。"""
    dates = _dates(days)          # 画面で選べる14日ぶん
    conn.execute("ATTACH ? AS old", (str(against),))

    gaps = []
    for name in sorted(set(seen) | set(prev)):
        empty = [d for d in dates if not seen.get(name, {}).get(d)]
        if not empty:
            continue
        # 前も0だったなら、その事業者は元からその日を持っていない（正常）
        newly = [d for d in empty if prev.get(name, {}).get(d)]
        gaps.append((name, empty, newly))
```

要点は `--against` で**前のDBと比べる**ところです。有効期間の短い
コミュニティバスは元から末尾の日付が空で、それは異常ではありません。
**「前は運行していたのに今は空」だけを異常として扱います。**

余談ですが、この直し自体もAIに書かせたところ、
**比較相手がないのに「取り込みで失われている」と断定する**コードが
最初に出てきました。実行してすぐ分かる誤りです。
書かせたものは動かして確かめる、という当たり前のところに戻ります。

取り込み手順はこの確認で止まるようにし、引っかかったら
再構築へ進まずに切り戻し手順を表示します。

## 学んだこと

**合計の指標は、区分ごとの全滅を隠します。**

「総数」「合計件数」「平均レスポンス」のような指標は、分布が崩れても
値が動きません。今回でいえば、正しい問いは
「便数は減っていないか」ではなく
「**これから使う日を、各事業者が覆っているか**」でした。

指標は、**利用者が実際にぶつかる単位**まで割るべきです。
このアプリなら「日付 × 事業者」。地域別の在庫なら「拠点 × 商品」、
配信なら「地域 × 端末種別」に当たると思います。

**そして、AIに安全確認を書かせるときは、確認の中身を人が疑うこと。**
コードの品質は高く出てきます。抜けるのは「何を確認すべきか」のほうで、
そこは指示した側の責任として残ります。
